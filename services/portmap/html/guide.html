1️⃣ Step 1 — enable WoL in the OS copy-paste, no reboot needed

Turns the NIC's magic-packet listener on now, and installs a tiny systemd unit so it survives reboots (drivers reset it to d on every boot otherwise).

noahlab / jesus / pablo — run the block on each (adjust IFACE)

# IFACE per node: noahlab=enp5s0  jesus=enp42s0  pablo=enp4s0
IFACE=enp5s0
sudo ethtool -s $IFACE wol g
sudo tee /etc/systemd/system/wol.service <<EOF
[Unit]
Description=Enable Wake-on-LAN on $IFACE
After=network.target

[Service]
Type=oneshot
ExecStart=/usr/sbin/ethtool -s $IFACE wol g

[Install]
WantedBy=multi-user.target
EOF
sudo systemctl daemon-reload && sudo systemctl enable wol.service
sudo ethtool $IFACE | grep Wake-on   # want: Wake-on: g

noah-desktop — netplan manages the NIC here, so persist it there instead

sudo ethtool -s enp5s0 wol g                       # immediate
sudo ethtool enp5s0 | grep Wake-on                 # confirm "Supports Wake-on" includes g
# persist: add "wakeonlan: true" under the enp5s0 ethernet in the netplan yaml
ls /etc/netplan/                                   # find the yaml
#   ethernets:
#     enp5s0:
#       wakeonlan: true        <-- add this line
sudo netplan apply

2️⃣ Step 2 — BIOS settings per machine needs a reboot + keyboard/monitor (or the crash cart)

Two settings matter everywhere: enable PCI-E/PME wake (lets the NIC power the machine on) and disable ErP/EuP deep-sleep (ErP cuts power to the NIC when off, which kills WoL). Third, for the three servers only: restore power after AC loss — after a power cut they come back on their own instead of staying dark until you notice. That one is a bigger real-world uptime win than WoL itself.

noahlab — Gigabyte B450M DS3H Del at boot

  • Settings → Platform Power (may be under M.I.T. on older F-revisions): ErP = Disabled, Wake on LAN = Enabled
  • Settings → Platform Power → AC BACK = Always On (power-loss auto-restart)

jesus — MSI PRO B550M-VC WIFI Del at boot

  • Settings → Advanced → Wake Up Event Setup: Resume By PCI-E Device = Enabled (this is MSI's WoL switch)
  • Settings → Advanced → Power Management Setup: ErP Ready = Disabled, Restore after AC Power Loss = Power On

pablo — Biostar B450MH Del at boot · menu names vary on Biostar

  • Advanced → ACPI Settings (or Wake Up Configuration): Wake on PME / PCIE Wake = Enabled
  • ErP/EuP option (often under Advanced or Power): Disabled
  • State After Power Failure / Restore AC Power Loss = Power On

noah-desktop — Gigabyte B550 EAGLE WIFI6 Del at boot

  • Settings → Platform Power: ErP = Disabled, Wake on LAN = Enabled
  • Leave AC BACK alone (you don't want the desktop booting itself after outages)
  • BIOS is F1 — launch firmware. Optional: update via Q-Flash (BIOS → F8) for AGESA/memory/fTPM fixes. Not required — virtualization is already confirmed working — so only bother if you hit instability. Don't power-cycle mid-flash.

Testing (do suspend first, then full poweroff)

# from the desktop (or noahlab, for waking the desktop):
ssh jesus 'sudo systemctl suspend'   # test 1: suspend
wake jesus                            # should come back in ~5s
ssh jesus 'sudo poweroff'             # test 2: full shutdown (needs the BIOS bits)
wake jesus                            # should cold-boot

⚠ The desktop's WiFi-bridge caveat

The desktop's ethernet runs through the TP-Link extender in client-bridge mode. Magic packets are plain broadcast UDP frames and bridges normally forward broadcasts, so this usually works — but two conditions must hold: the extender stays powered (the sleeping NIC keeps its link to the extender, not the router), and the extender forwards broadcast traffic toward its wired client (most TP-Links do; a few do aggressive MAC-translation filtering). The suspend test above is the definitive answer — if wake desktop from noahlab works through the bridge once, it'll keep working. If it doesn't, waking the desktop remotely isn't possible over that link; everything else (the three nodes on real ethernet) is unaffected.

So yes — the box is ready, no BIOS changes needed for this. For Play Store games specifically, Waydroid (an Android container, near-native speed) beats the Android Studio emulator. Install:

curl -s https://repo.waydro.id | sudo bash
sudo apt install waydroid
sudo waydroid init -s GAPPS          # GAPPS = with Play Store
waydroid session start &
waydroid show-full-ui

Play certification (Play Store shows "device not certified" until you do this):

sudo waydroid shell -- sqlite3 /data/data/com.google.android.gsf/databases/gservices.db \
  "select value from main where name = 'android_id';"
# paste that number at https://www.google.com/android/uncertified — takes ~20 min to clear

ARM-only games: many Play games ship ARM-only builds. Install a translation layer with waydroid_script — pick libndk (better on AMD CPUs than libhoudini). The same script can install Magisk if a game demands it.

Straight talk: games enforcing Play Integrity / hardware attestation (some gacha titles, most banking-grade apps) will detect the container and refuse regardless of setup. Most games work; those won't. Fallback for a stubborn title: Android Studio's emulator with a Play Store x86_64 image — slower, but a different detection profile. KVM is already set up for it.
